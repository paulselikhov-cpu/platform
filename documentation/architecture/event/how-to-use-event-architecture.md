# Как пользоваться event-архитектурой (инструкция для разработчика)

> Эта инструкция — для того, кто плохо знает бэкенд (например, фронтендер),
> но хочет понимать, как работает событийная архитектура BabichChat, и
> грамотно реализовывать сценарии. Все термины объясняются «по-человечески»,
> с отсылками на реальные файлы кода.
>
> Если контекст потерян — читать этот файл первым, затем
> [`event-migration-plan.md`](event-migration-plan.md) (что уже сделано)
> и [`babichchat-event-architecture.md`](babichchat-event-architecture.md) (зачем это всё).

---

## 1. Главная идея одним предложением

> **Действие** в системе меняет состояние и **публикует факт** (событие).
> Кто и как на этот факт отреагирует — решают **независимые подписчики**,
> а не тот код, который действие запустил.

---

## 2. Аналогия с фронтендом (как понять за 2 минуты)

Во Angular есть `@Output()`-событие: компонент не вызывает родителей напрямую,
а только *эмитит* событие с данными. Кто на него подпишется и что сделает —
решает родительский шаблон:

```ts
// Компонент-кнопка просто сообщает факт:
this.somethingHappened.emit({ id, amount });
```

```html
<!-- Родитель сам решает, что делать с этим фактом: -->
<app-button (somethingHappened)="onSomething($event)" />
```

В BabichChat на бэкенде — ровно та же логика, только масштаб побольше:

| Angular | Бэкенд BabichChat |
|---------|-------------------|
| `@Output() somethingHappened` | `DomainEventPublisher.publish(new SomeEvent(...))` |
| объект `{ id, amount }` | `DomainEvent` с полями `actorId`, `targetId`, `scopeId`, `payload` |
| `(somethingHappened)="onSomething($event)"` | `@ApplicationModuleListener` на методе-подписчике |
| родительский шаблон решает, что делать | каждый подписчик сам решает, что делать |
| один эмит — много обработчиков в разных родителях | одно событие — много независимых подписчиков |

Ключевое отличие от «лобовых» вызовов (`serviceA.callServiceB()`):
когда новое последствие появляется позже (уведомление, квест, аудит, запуск
другого процесса), его добавляют **отдельным подписчиком**, а НЕ правят
существующий код действия. Действие не знает и не должно знать, кто его слушает.

## 3. Словарик простыми словами

Это реальные классы из `babich-app/src/main/java/com/platform/...`.

### 3.1. `DomainEvent` — «конверт события» (`core/event/DomainEvent.java`)
Абстрактный класс — шаблон для всех событий. Каждый конверт несёт:
- **`type`** — что произошло (см. `EventType` ниже);
- **`actorId`** — *кто* инициатор (может быть `null`, если событие системное, например закрытие по таймеру);
- **`targetId`** — *кому* адресовано;
- **`scopeType` / `scopeId`** — *где* это случилось (район, персонаж, парламент);
- **`payload`** — *доп. данные* (карта «ключ→значение»), любые бизнес-данные, которые нужны подписчикам.

Важно: событие **не хранится в БД как бизнес-сущность** — это транспортный
объект. Если подписчику надо что-то сохранить (уведомление, аудит), он делает
это сам, у себя в таблицах.

### 3.2. `EventType` — реестр всех событий (`core/event/EventType.java`)
Просто enum-список: `POLL_CLOSED`, `ELECTION_CLOSED`, `COINS_CHANGED`,
`XP_CHANGED`, `APPLICATION_RESOLVED`, `NOTIFICATION_SENT`, `CAMPAIGN_FINISHED`,
`POLL_CREATED`. Новое событие начинается с добавления значения сюда.

### 3.3. `ScopeType` — «где случилось» (`core/event/ScopeType.java`)
`CHARACTER` (персонаж), `DISTRICT` (район), `PARLIAMENT`, `GANG`.

### 3.4. `DomainEventPublisher` — «рупор» (`core/event/DomainEventPublisher.java`)
Единственная точка, через которую код *кричит* событие:
```java
eventPublisher.publish(new SomeEvent(...));
```
Никто больше не «кричит» напрямую в `ApplicationEventPublisher` — только через
этот класс. Заменяет транспорт (сейчас Spring Events, потом Kafka) без правки
публикаторов и подписчиков.

### 3.5. `@ApplicationModuleListener` — «я подписан»
Аннотация на методе подписчика. Говорит: «вызови меня, когда такое событие
опубликуют». Три важные особенности:

**AFTER_COMMIT — это не место в коде, а момент времени.** Внутри `@Transactional`-
метода событие не уходит сразу — оно «прикладывается» к операции, как записка к
черновику. Дальше только два исхода:
- метод дошёл до конца → **commit** → и сразу ПОСЛЕ него Spring раздаёт события
  подписчикам (это и есть AFTER_COMMIT);
- внутри что-то упало → **rollback** → черновик и записки выбрасываются →
  подписчики НЕ вызываются.
Гарантия: подписчик никогда не сработает для операции, которая не завершилась
успешно.

**Outbox-гарантия** — событие пишется в техническую таблицу `event_publication`
в транзакции публикатора и будет доставлено даже после перезапуска, если
сервер упал между коммитом и обработкой. Это «надёжность доставки», которую
вручную писать не пришлось — её даёт Spring Modulith.

**Почему нельзя ставить свою `@Transactional`:** подписчик вызывается на
отдельном потоке, уже ПОСЛЕ того, как исходная транзакция закончилась. Значит,
в этот момент «текущей» транзакции нет. А обычная `@Transactional` значит
«присоединись к текущей, а если нет — открой новую» — этого Spring/Modulith на
`@ApplicationModuleListener` не позволяет. Разрешены только:
- `REQUIRES_NEW` — «всегда открывай свежую, независимую транзакцию» (пример —
  `TransactionLogEventListener`, аудит пишется сам по себе);
- `NOT_SUPPORTED` — «работай без транзакции»;
- ничего — метод просто бежит без транзакции, а каждая запись внутри сама
  открывает свою маленькую транзакцию (пример — `NotificationEventListener`:
  у него нет `@Transactional`, но `notificationService.notify()` помечена
  `@Transactional`, поэтому одно уведомление = одна транзакция).

> **Не путай две стороны одного события!** Правило выше касается ТОЛЬКО
> подписчика (метода с `@ApplicationModuleListener`). На стороне **публикатора**
> (`RewardService.giveCoins`, где вызывается `publish(...)`) своя `@Transactional`
> — наоборот, **нужна**: именно её commit отпускает событие подписчикам.
>
> | | Публикатор | Подписчик |
> |---|---|---|
> | Где | метод, который зовёт `eventPublisher.publish(...)` | метод с `@ApplicationModuleListener` |
> | Пример | `RewardService.giveCoins` | `TransactionLogEventListener.onCoinsChanged` |
> | Своя `@Transactional` | ✅ нужна | ❌ обычная нельзя (только `REQUIRES_NEW`/`NOT_SUPPORTED`) |

### 3.6. События с особым смыслом
- `CoinsChangedEvent` / `XpChangedEvent` — «баланс монет/XP изменился»; подписчик
  `TransactionLogEventListener` пишет аудит в `TransactionLog`.
- `ElectionClosedEvent` — «выборы закрыты, вот победитель»; подписчик
  `NotificationEventListener` шлёт уведомления жителям + WS-пуш.
- `ApplicationResolvedEvent` — «гражданская заявка решена (APPROVED/REJECTED)»;
  тот же подписчик уведомляет заявителя (адресно по `characterId`, в
  `Notification.data` кладёт applicationType/applicationStatus).
- `PollClosedEvent` — «голосование закрыто и обработано» (общее для всех типов голосования).

### 3.7. `PollResultHandler` + `PollResultDispatcher` — «последствия голосования»
Паттерн **стратегия**: для каждого типа голосования (`PollType`) есть своя
реализация `PollResultHandler` (метод `supportedTypes()` + `handle(poll)`).
`PollResultDispatcher` собирает все реализации через Spring, строит карту
`PollType → handler` и при закрытии голосования вызывает нужный.

Новый тип голосования = **новая реализация интерфейса**, а не правка фасада.

### 3.8. `ScheduledCheck` / `TickHandler` — «таймеры»
Вместо разрозненных `@Scheduled` есть единый `SchedulerGateway`. Периодические
задачи — через `TickHandler` (например, presence-обновления каждые 15 сек),
отложенные проверки — через реестр `ScheduledCheck` (например, закрыть выборы,
когда истёк `endsAt`).

## 4. Жизненный цикл сценария целиком (стрелочная схема)

```
[Фронтенд: игрок нажал кнопку]
   │  REST-запрос (или WS-команда)
   ▼
[Controller] ─── Слой "вход", тонкий, только парсит запрос
   │
   ▼
[Facade] ─── Слой 2, "сценарий": собирает шаги в один вызов, понятный клиенту
   │           (ElectionFacade.initiateElection / closeElection / ...)
   │
   ▼
[Service] ─── Слой 3, "бизнес-логика": валидация + изменение состояния в БД
   │
   │  (в той же транзакции)
   ▼
[DomainEventPublisher.publish(new SomeEvent(...))]  ─── публикация факта
   │
   ▼
[event_publication + AFTER_COMMIT]  ─── событие надёжно доставлено ПОСЛЕ коммита
   │
   ▼
[Подписчики @ApplicationModuleListener] ─── Слой 4, независимые реакции:
   ├─ NotificationEventListener  → сохранить Notification + WS-пуш
   ├─ TransactionLogEventListener→ записать аудит
   ├─ (будущее) QuestService     → продвинуть квест
   └─ ...
        │
        ▼
   [WS-пуш: /user/{username}/queue/notifications]
        │
        ▼
[Фронтенд других игроков видит уведомление / обновление]
```

Зоны ответственности:
- **Фронтендер управляет**: как выглядит действие, какой REST/WS он шлёт, как
  принимает WS-пуш и перерисовывает UI.
- **Бэкенд управляет**: сценарием (Facade), бизнес-логикой (Service), фактом
  (событие) и последствиями (подписчики).

Фронтендеру не нужно понимать каждый Java-класс — ему достаточно знать
**контракт события** (какие данные уйдут подписчикам и, главное, какие
данные в итоге прилетят обратно на фронт).

## 5. Пошаговый рецепт «новый сценарий на событиях»

Это универсальная последовательность. Пример — «Обжаловать губернатора»
(вторая итерация сценария выборов) или любой будущий сценарий.

### Шаг 0. Определи «факт» (главное!)
Подумай: **что произошло** — одно именованное событие. Не «что я хочу сделать
потом», а «что уже случилось и о чём мир должен узнать».
Плохо: «уведомить игроков». Хорошо: «выборы закрыты», «заявка одобрена».

### Шаг 1. Заведи событие в коде
- Добавь значение в `EventType` (если такого ещё нет).
- Создай класс `SomeEvent extends DomainEvent` в `core/event/`, конструктор
  заполняет `type`, `actorId/targetId/scopeType/scopeId` и кладёт данные в `payload`.
- **Зарегистрируй** его в `@JsonSubTypes` у `DomainEvent` (список известных
  событий). Без этого событие не десериализуется при replay из `event_publication`.

### Шаг 2. Публикуй факт
«Опубликовать» — это НЕ отправить что-то по сети и НЕ вызвать подписчиков сразу.
Это сказать Spring-у: «вот что случилось». Spring запоминает событие (пишет его
в техническую таблицу `event_publication`) и уведомит подписчиков ПОЗЖЕ — только
после успешного завершения транзакции (AFTER_COMMIT).

Поэтому публикуй событие ВНУТРИ той же операции, что меняет состояние, — так
делает `RewardService`:
```java
@Transactional
public void giveCoins(Long userId, long amount, RewardReason reason, Long relatedEntityId) {
    ChatUser user = getUser(userId);
    user.setCoinBalance(user.getCoinBalance() + amount);      // 1. меняем состояние
    chatUserRepository.save(user);                            // 2. сохраняем в БД
    eventPublisher.publish(
            new CoinsChangedEvent(userId, amount, reason, relatedEntityId)); // 3. публикуем факт
}
```
Из-за `@Transactional` все три строки — один «черновик» (транзакция): пока он не
завершится, изменения никому не видны. Публикация события входит в этот же черновик.
Дальше только два исхода:
- **Всё успешно → commit.** Черновик применяется, и только ПОТОМ (AFTER_COMMIT)
  вызываются подписчики — они видят уже реально сохранённое состояние.
- **Что-то упало → rollback.** Черновик отбрасывается целиком, и событие вместе
  с ним. Подписчики НЕ вызываются.

Отсюда главная гарантия: **подписчик никогда не сработает для операции, которая
не докрутилась до конца** — не бывает «уведомления о начислении, а монет не дали».

`DomainEventPublisher` уже инжектится через конструктор (в `RewardService` это
поле `private final DomainEventPublisher eventPublisher;` + `@RequiredArgsConstructor`).
Тебе остаётся только вызвать `eventPublisher.publish(new SomeEvent(...))` в том же
методе, где изменяется состояние.

**Главное правило:** не публикуй событие «потом», отдельным вызовом, после того
как метод с изменением уже закончился — между «изменил состояние» и «сообщил об
этом» может вклиниться ошибка, и гарантия выше сломается.

### Шаг 3. Напиши подписчика
Класс `@Component` с методом `@ApplicationModuleListener`, который принимает
твоё событие и делает нужный побочный эффект (уведомление, WS-пуш, аудит,
запуск чего-то). Один подписчик — одно «семейство» последствий; разные
последствия — разные методы/классы.

### Шаг 4. Если это голосование — добавь обработчик в диспетчер
Реализуй `PollResultHandler` (укажи `supportedTypes()`), и `PollResultDispatcher`
сам найдёт его по типу. Фасад/сервисы не меняются.

### Шаг 5. Проверь по DoD
См. раздел 7 — «не забыть».

## 6. Живые примеры из кода (разбор трёх цепочек)

### Пример А. Монеты: «списали/начислили» → аудит
1. `RewardService.giveCoins/takeCoins` публикует `CoinsChangedEvent`.
2. `TransactionLogEventListener` (`@ApplicationModuleListener`) ловит его.
3. Пишет строку в `TransactionLog` (COIN/XP_USER) — это аудит.
   Почему не синхронно в RewardService? Чтобы RewardService не знал про
   TransactionLog и любое новое последствие добавлялось подписчиком.

### Пример Б. Заявка: «решена» → уведомление заявителя + обновление профиля
1. `ApplicationService` после `handler.handle()` + save публикует
   `ApplicationResolvedEvent` и (для заявок, меняющих ChatUser)
   `CharacterUpdatedEvent`.
2. `NotificationEventListener.onApplicationResolved` ловит первый:
   по `characterId` находит персонажа, сохраняет `Notification`
   (в `data` — applicationType/applicationStatus) и шлёт WS-пуш в
   `/user/{username}/queue/notifications`.
3. `CharacterUpdatedListener` ловит второй: WS-пуш в
   `/user/queue/character-updated` → фронт перезагружает профиль
   (`CurrentChatUserService.refresh()`), см. architecture/reactive-character-updates.md.

### Пример В. Выборы: «закрылись» → назначение + уведомление всем
1. `ElectionFacade.closeElection` (Слой 2) закрывает голосование через
   `PollService` (Слой 3) — всё в одной транзакции.
2. `PollResultDispatcher.dispatch(closed)` выбирает `ElectionResultHandlerAdapter`
   по `PollType.ELECTION` (Слой 4) — тот назначает губернатора в `LocationPost`
   и **сам** публикует `PollClosedEvent`.
3. Фасад публикует `ElectionClosedEvent` (с именем победителя).
4. `NotificationEventListener.onElectionClosed` ловит `ElectionClosedEvent`,
   рассылает «Губернатором избран ...» всем жителям района + WS-пуш.

Обрати внимание: у `closeElection` два «выхода» (два события), и каждое
обрабатывает свой подписчик. Фасад не вызывает NotificationService напрямую —
это и есть суть рефакторинга: **Слой 3 публикует, Слой 4 слушает.**

## 7. Чек-лист DoD (что должен сделать бэкенд, чтобы сценарий считался готовым)

1. **Событие зарегистрировано** в `@JsonSubTypes` у `DomainEvent` и значение
   добавлено в `EventType` (иначе replay сломается).
2. **Публикация в той же транзакции**, что и бизнес-изменение.
3. **Подписчик** с `@ApplicationModuleListener`; у него **нет** собственной
   `@Transactional`, кроме `REQUIRES_NEW`/`NOT_SUPPORTED`.
4. **Событие — только для необязательных последствий.** Всё, что обязано
   случиться атомарно (списание + выдача роли), — синхронный вызов внутри
   сервиса, а не событие. Иначе обязательный эффект можно случайно превратить
   в «может быть, случится».
5. **Границы модулей**: публикатор и подписчик не импортируют друг друга
   напрямую, общаются только через событие в `core.event`.
6. **Два теста**:
   - тест факта публикации (`@RecordApplicationEvents`) — сервис действительно
     опубликовал событие с верным payload;
   - тест сквозного пути (Modulith `Scenario`) — подписчик реально отработал
     и дал эффект (запись в БД / WS-пуш). Без него легко получить ложно-зелёный
     тест на подписчике, который никогда не вызывается.
