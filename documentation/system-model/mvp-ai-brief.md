# BabichChat — бриф для AI-разработчика: MVP экономического и ролевого слоя

> **Кратко:** Техническое задание на MVP — минимальный связный цикл экономики и ролей.
> Что уже реализовано: экономический слой (монеты, XP, энергия, RewardService),
> профессия «дворник», покупка первой локации через заявку, система районов.
> Что предстоит: группировки (Воры, Проститутки), полицейский участок, банк, рынок.
> Порядок реализации — раздел 6.
>
> **Оглавление:**
> - Раздел 0 — Что уже есть (отправная точка)
> - Раздел 1 — Скоуп MVP (что делаем, что откладываем)
> - Раздел 2 — Базовый экономический цикл
> - Раздел 3 — Группировки: Воры и Проститутки
> - Раздел 4 — Структуры: полиция, банк, рынок
> - Раздел 5 — Роли (список сущностей)
> - Раздел 6 — Итоговый порядок реализации (главное!)

Этот документ адресован AI-агенту, который будет дорабатывать существующий backend
(Java/Spring) и frontend (Angular) чата. Он написан как техническое задание поверх
общей концепции (`babichchat_concept.md, districts-and-public-locations.md`), но сужен до **первого работающего MVP**:
минимального, но полностью связного цикла, который потом расширяется модульно.
Приоритет — реализовать функционал из концепции; существующий код при этом можно и
нужно менять, если это требуется для результата, а не сохранять в неизменном виде
любой ценой.

## 0. Что уже есть (отправная точка, а не жёсткое ограничение)

Текущий код — уже рабочий каркас онлайн-чата (backend на Java/Spring, frontend на
Angular). Базовые сущности вроде пользователя, локаций (публичных/приватных),
каналов внутри локации и сообщений уже реализованы и работают — изучи фактический
код, а не описания, чтобы понять точную текущую структуру данных и API.

Твоя задача — нарастить поверх этого экономический слой (монеты, XP, энергия),
ролевую систему и первые игровые структуры, ориентируясь в первую очередь на
**достижение функционала из концепции**, а не на сохранение существующих сущностей
любой ценой. Если для реализации задуманного функционала существующую сущность
нужно расширить полями, изменить связи или переписать — делай это; переиспользование
кода приветствуется, но не в ущерб результату. Ориентиры:
1. В итоге должен получиться один **связный цикл**, который реально проходится от
   начала до конца: житель без денег и локации → зарабатывает → покупает первую
   локацию → может пойти в группировку или структуру → зарабатывает там → тратит.
2. Новые игровые сущности (экономика, роли, группировки, структуры) стоит по
   возможности отделять собственными таблицами/сервисами (см. раздел 8), чтобы дальше
   их можно было независимо расширять — но это ориентир, а не догма важнее
   работающего функционала.

## 1. Скоуп MVP (что делаем сейчас, что откладываем)

### Делаем сейчас
1. Экономический слой: монеты, XP-USER, энергия, единый сервис начислений
   (`RewardService`) с логом транзакций.
2. Статус «бомж» → профессия «дворник» (тап-фарм) → покупка первой локации.
3. **Упрощённая мэрия** — не полноценная система голосований, а минимальный сервис
   одобрения заявок (для MVP можно автоматически одобрять заявки на покупку первой
   локации/вступление в группировку — но через ту же структуру данных `Application`
   (заявка), чтобы в будущем заменить автоодобрение на реальное голосование без
   переделки модели).
4. Две группировки: **Воры** и **Проститутки** (см. раздел 3).
5. Одна гражданская структура: **Полицейский участок** (`civic_role`, упрощённая
   версия — см. раздел 4.1).
6. Один chatUser.civic_role= DIRECTOR-сервис: **Банк** (упрощённая версия — см. раздел 4.2).
7. **Рынок (общий)** — аренда прилавков без мэрии (см. раздел 4.3).

### Закладываем архитектурно, но НЕ реализуем логику сейчас
- **Рынок недвижимости** — завести сущность-заглушку (например, таблицу `Listing`
  с полями locationId, sellerId, price, status), но бизнес-логику купли-продажи,
  комиссию chatUser.civic_role= DIRECTOR-владельца рынка и т.д. не писать. Это отдельный будущий
  модуль.
- Полноценная мэрия с Парламентом, «Площадью Ленина», голосованиями, каскадным
  распределением энергии между структурами — архитектурно предусмотрена (см. раздел
  8), но в MVP работает в упрощённом/заглушечном виде.
- Мини-игры, кастомизация, дневные квесты, остальные виды бизнеса (клуб, кафе,
  мебельный и т.д.) — не в этой итерации.

## 2. Базовый экономический цикл MVP

```
Регистрация → житель без локации ("бомж")
      → работает дворником (тап-фарм, тратит энергию, получает монеты + чуть XP)
      → копит монеты → покупает первую локацию (студия-хрущёвка) через упрощённую
        заявку в мэрию (в MVP — автоодобрение)
      → теперь у жителя есть локация → появляется личная спальня для восстановления
        энергии (см. 2.3)
      → житель может: (а) продолжать качать профессию, (б) вступить в группировку
        (Воры или Проститутки) по приглашению, (в) устроиться в структуру
        (полицейский участок), (г) арендовать прилавок на рынке
      → заработанные монеты тратятся: аренда/содержание локации, покупка вклада в
        банке, покупка товара для прилавка и т.д.
```

### 2.1 Сущности экономики
- `CoinBalance` (у User) — просто числовое поле или отдельная таблица с историей.
- `XpUser`, `XpGang` — накопительные счётчики, никогда не уменьшаются.
- `Energy` — текущее значение + таймстамп последнего пересчёта (чтобы не хранить
  тикающий таймер, а вычислять «сколько накопилось» на лету при каждом запросе).
- `RewardService` — единая точка входа для любого начисления/списания монет и XP,
  принимает `reason` (enum: `WORK_SHIFT`, `GANG_TRIBUTE`, `POLICE_FINE`,
  `BANK_INTEREST`, `MARKET_SALE` и т.д.) и пишет запись в `TransactionLog`.

### 2.2 Профессия «дворник» (единственная профессия MVP)
- Тап-действие: житель нажимает кнопку «работать», сервис проверяет остаток
  энергии, списывает фиксированную порцию энергии, начисляет фиксированную монету
  (+ немного XP-USER) через `RewardService`.
- Rate-limit на уровне API обязателен даже для MVP (защита от скриптового спама
  кнопки).

### 2.3 Энергия в MVP
- Восстановление: упрощённо — пассивный таймер (+1 каждые N минут), без полноценной
  механики сна на старте. Разделение по локации/уровню (потолок 30–50% от сна) можно
  добавить отдельной итерацией — заложи в модели поле `energyRegenSource`
  (`PASSIVE`/`SLEEP`/`FOOD`), чтобы потом не переделывать таблицу.
- Кулдауны и текущая энергия — в Redis (TTL), не в клиентском времени.
  Целевая роль Redis шире TTL: это realtime-хранилище проекта (presence, счётчики,
  кулдауны/квоты) при целевом онлайне 100k+; внешний STOMP-брокер для fan-out —
  RabbitMQ/Artemis через StompBrokerRelay. См.
  [`architecture/realtime/scale-targets-and-redis.md`](../architecture/realtime/scale-targets-and-redis.md).

### 2.4 Заявки (`Application`)
Даже для MVP заведи заявки как отдельную сущность с полем `type` (enum,
расширяемый): `BUY_FIRST_LOCATION`, `JOIN_GANG` и т.д. Обработчик для каждого типа —
отдельный класс/сервис (стратегия). В MVP большинство типов просто автоодобряются
сразу после создания — но структура данных (кто подал, когда, какой статус, кто
рассматривал) должна уже поддерживать будущую замену на реальное голосование.

## 3. Группировки: Воры и Проститутки (первые две в MVP)

### 3.1 Общая для обеих группировок модель данных
- `Gang` (id, type: `THIEVES`/`PROSTITUTES`, name, level, treasuryBalance, energyPool).
- `GangMember` (userId, gangId, nicknameGang — скрытый ник, hierarchyPostId).
- `GangHierarchyPost` (gangId, title, slotsCount, minXpGang, canParticipateInExile —
  флаг для механики свержения лидера, вне скоупа MVP, но поле можно завести сразу).
- `GangLocation` — отдельная приватная `Location`, видимая только участникам банды
  (используй существующий тип Location с флагом `visibility = GANG_ONLY` и привязкой
  к `gangId`).
- Вступление — только по приглашению лидера/по заявке через `Application` типа
  `JOIN_GANG`.
- У обеих группировок в статусе жителя (публичном профиле) отображается **фейковая
  профессия** — например «дворник» или «швея» — вместо реальной механики; реальный
  заработок идёт через `chatUser.gang_role`, не через `profession`.

### 3.2 Группировка «Воры» (эталонный пример для симметрии)

**Идея:** участник не работает по обычной профессии — вместо этого совершает
«кражи», результат которых уходит в общак банды, а сам участник получает
«зарплату» из общака.

**Механика по шагам:**
1. Участник инициирует действие «пойти на дело» (аналог тап-фарма/смены, тратит
   энергию, есть кулдаун).
2. Сервис бросает бросок (шанс успеха зависит от `XpGang` участника и, опционально,
   от «защищённости» цели/локации — в MVP можно упростить до фиксированного
   процента успеха).
3. При успехе: в общак банды (`treasuryBalance`) зачисляется случайная сумма монет
   (диапазон растёт с уровнем `XpGang` участника), сам участник получает XP-GANG,
   плюс фиксированную «зарплату» из общака (через `RewardService`, `reason:
   GANG_TRIBUTE`).
4. При провале: риск — сообщение в лог полиции (см. 4.1) с шансом, что полицейский
   позже «спалит» участника, вбив его никнейм в базу.
5. Украденные предметы (если есть инвентарная механика — вне MVP) в будущем можно
   перепродавать на рынке под другим названием — не реализуем в MVP, но сущность
   `MarketListing` стоит сразу иметь поле `originalItemId` (nullable) под эту
   будущую логику подмены.

**Анти-фрод:** лимит успешных «дел» в сутки на одного участника (через Redis TTL,
как у энергии).

### 3.3 Группировка «Проститутки» (детализируем по аналогии с «Ворами»)

**Идея:** та же схема «фейковая публичная профессия → скрытая монетизация через
приватные платные встречи с другими жителями → общак → зарплата», но вместо
случайного «броска на успех кражи» — это **сделка с согласия двух сторон**
(житель-клиент сам инициирует и платит).

**Механика по шагам:**
1. Участница/участник группировки открывает у себя в профиле (видно только тем, кто
   знает — например, через отдельный публичный тег `escortAvailable`, не выдающий
   принадлежность к банде) предложение платной «встречи» с указанием цены в
   монетах. Цена может расти вместе с `XpGang` — чем выше уровень, тем выше
   допустимый ценовой диапазон (упрощённо: `minPrice`/`maxPrice`, вычисляемые от
   `XpGang`).
2. Другой житель (клиент) инициирует заявку на «встречу» в приватной локации
   (например, в своей или её квартире).
   Клиент подтверждает оплату согласованной суммы монет.
3. Сервис списывает монеты у клиента и делит сумму:
   - Основная часть уходит в общак банды (`treasuryBalance`), как «дань» —
     аналогично тому, как у воров украденное уходит в общак.
   - Небольшой фиксированный процент участница получает на руки сразу (личные
     монеты, чтобы бы была ощутимая моментальная награда, а не только зарплата
     из общака).
   - Участница получает **XP-USER** напрямую за «встречу» (в отличие от воров, где
     основной выход — монеты в общак, здесь по замыслу концепции акцент на
     получении опыта, а не денег напрямую).
4. Периодически (как и у воров) участница получает «зарплату» из общака —
   `RewardService`, `reason: GANG_TRIBUTE`.
5. Риск разоблачения — тот же полицейский механизм (4.1): полицейский, заметив
   подозрительную частоту приватных «встреч» жителя, может попытаться вбить в базу
   её `nicknameGang`; при правильной догадке — полицейский получает награду и метку
   ставится в полицейскую базу, при ошибке — полицейский несёт наказание (см. 4.1).

**Анти-фрод:** лимит на количество оплаченных «встреч» с одним и тем же клиентом в
сутки (та же логика лимита пары пользователей, что у реакций/подарков/краж — не
даём двум сговорившимся аккаунтам бесконечно перекачивать монеты друг другу под
видом «встреч»).

**Данные:** заведи отдельную таблицу `EscortSession` (gangMemberId, clientId,
price, xpAwarded, gangCut, personalCut, timestamp, locationId) — по аналогии можно
завести `TheftAttempt` (gangMemberId, success, amount, timestamp) для воров, чтобы
обе группировки имели симметричную, но раздельную историю транзакций для
анти-фрода и будущей аналитики.

## 4. Структуры MVP: полицейский участок, банк, рынок

Формат ниже — как конкретный проходимый сценарий (по аналогии с примером
«pashaSelikhov» из базовой концепции), чтобы было видно, как это работает от
кнопки до записи в базе.

### 4.1 Полицейский участок (`civic_role`, упрощённая версия)

**Роль:** `POLICE_OFFICER` — назначается вручную (для MVP: администратором
платформы/через упрощённую заявку без полноценного голосования мэрии). Слотов на
район — фиксированное небольшое число (например, 3).

**Энергия в MVP:** пока нет полноценной каскадной системы мэрии (раздел 8 базовой
концепции), у каждого `POLICE_OFFICER` — **фиксированная дневная квота энергии**
(например, 20 очков в сутки, хранится в Redis с TTL до полуночи). Позже эта квота
заменяется на каскадное распределение от структуры/губернатора — без изменения
того, как сама роль тратит энергию.

**Действия и их стоимость (пример):**
| Действие | Энергия | Эффект |
|---|---|---|
| «Оштрафовать» | 2 | Списывает монеты у указанного жителя, часть уходит в бюджет мэрии (`reason: POLICE_FINE`) |
| «Составить протокол» | 1 | Косметическая запись в публичном логе локации, без экономического эффекта |
| «Проверить на связь с группировкой» | 5 | См. сценарий ниже |

**Сценарий (по образцу базового примера):**
1. Полицейский Иванов подозревает, что житель с ником `pashaSelikhov` состоит в
   группировке «Воры» (например, заметил частые заявки `TheftAttempt` с провалом
   рядом с этим жителем, или просто по RP-логике).
2. Иванов открывает форму «Проверить на связь с группировкой» в интерфейсе
   участка, вводит целевого жителя и предполагаемый тип группировки.
3. Сервис сверяет реальную запись `GangMember.nicknameGang` (скрыто от всех, кроме
   этой проверки) с введённым предположением.
4. Если совпадение — начисление монет Иванову (`RewardService`, `reason:
   POLICE_GANG_CATCH`) + запись в публичную полицейскую базу
   (`PoliceRecord: userId, gangType, catchDate, officerId`).
5. Если совпадения нет — штраф самому Иванову: понижение его `XpGang`-аналога для
   civic_role (условно «звание» полицейского) или временная блокировка действия
   «Проверить на связь» на сутки (реализуй как самое простое наказание для MVP —
   например, откат потраченной энергии не даём, плюс кулдаун-штраф).

### 4.2 Банк (`chatUser.civic_role= DIRECTOR`, упрощённая версия)

**Роль:** `BANK_DIRECTOR` — один слот на район, назначается (для MVP — вручную
администратором/автозаявкой). Без директора банк не принимает новые вклады
(read-only витрина).

**Действия жителя:**
- «Открыть вклад» — житель вносит сумму монет на фиксированный срок под
  фиксированный процент (в MVP — жёстко закодированная ставка, например 5% за 3
  дня, без реального рынка ставок).
- «Забрать вклад» — доступно только после истечения срока; при досрочном
  закрытии — без процентов (штраф за досрочность, простая логика для MVP).

**Сценарий:**
1. Житель Смирнова открывает вклад на 500 монет на 3 дня под 5%.
2. Сервис списывает 500 монет со счёта Смирнова, создаёт запись `Deposit`
   (userId, amount=500, rate=0.05, openedAt, maturesAt, status=ACTIVE).
3. Фоновая задача (шедулер) проверяет каждый день истёкшие вклады.
4. По истечении срока: Смирнову начисляется 500 + 5% = 525 монет
   (`RewardService`, `reason: BANK_INTEREST`); из процента часть (например, 1 из
   5 процентных пунктов) уходит в бюджет мэрии как комиссия банка
   (`reason: BANK_FEE_TO_TREASURY`) — это то, что «кормит» мэрию, по базовой
   концепции.

**Данные:** `Deposit` (id, userId, amount, rate, openedAt, maturesAt, status).

### 4.3 Рынок (общий, аренда прилавков — единственный бизнес без мэрии)

**Роль:** `chatUser.civic_role = BUSINESSMAN` типа `MARKET_STALL_OWNER` — выдаётся сразу при аренде,
без заявки в мэрию (в отличие от «настоящего» бизнеса).

**Сценарий:**
1. Житель Кузнецова арендует прилавок за 50 монет на сутки (`MarketStall`:
   id, ownerId, rentedUntil).
2. Кузнецова становится `chatUser.civic_role = BUSINESSMAN` (MARKET_STALL_OWNER) и получает доступ к
   личному мини-складу прилавка (`StallInventory`: stallId, itemId, quantity,
   pricePerUnit).
3. Кузнецова закупает товар на системном складе (или вручную заводит позиции для
   MVP, если склад ещё не реализован) — например, 10 единиц «самогона» по 2 монеты
   за штуку закупки, выставляет на прилавке по 5 монет за штуку.
4. Другой житель заходит на локацию «Рынок», видит прилавок, покупает 1 единицу —
   сервис списывает 5 монет у покупателя, зачисляет их в кассу прилавка
   (`StallCashbox`), уменьшает `quantity` на 1.
5. Кузнецова заходит и «снимает кассу» — деньги переводятся на личный баланс
   (`RewardService`, `reason: MARKET_SALE`).
6. По истечении срока аренды (`rentedUntil`), если не продлить — прилавок
   закрывается, `chatUser.civic_role = BUSINESSMAN` снимается, остаток товара «сгорает» или
   возвращается в личный инвентарь (реши по вкусу, не критично для MVP).

**Анти-АФК:** фоновая задача проверяет истёкшую аренду и деактивирует прилавки.

### 4.4 Рынок недвижимости (только сущность-заглушка, без логики)

Заведи `RealEstateListing` (id, locationId, sellerId, price, status: `DRAFT` —
и больше ничего). Не подключай никакой бизнес-логики купли-продажи, комиссии
`chatUser.civic_role= DIRECTOR`-владельца рынка и т.п. — это осознанно отложено на следующую
итерацию после того, как MVP-цикл заработает.

## 5. Роли — итоговый список сущностей для MVP

Заведи с самого начала пять отдельных таблиц/сервисов (даже если некоторые в MVP
почти пустые) — это тот же принцип, что и в базовой концепции:

- `Profession` (пока только `DVORNIK`)
- `chatUser.civic_role = BUSINESSMAN` (пока только `MARKET_STALL_OWNER`)
- `chatUser.civic_role= DIRECTOR` (пока только `BANK_DIRECTOR`)
- `civic_role` (пока только `POLICE_OFFICER`)
- `chatUser.gang_role` (у каждого `GangMember` — привязка к `GangHierarchyPost`)
- `SystemRole` (admin/moderator — обычный RBAC, не связан с игровой логикой)

Не объединяй их в одну таблицу «roles» с полем type — это тот момент, который
позже больнее всего аукнется при расширении (полномочия/лимиты/энергия у каждого
типа принципиально разные).

## 6. Итоговый порядок реализации (рекомендуемый)

1. `RewardService` + `TransactionLog` + монеты/XP-USER/энергия поверх
   существующего `User`.
2. Профессия «дворник» (тап-фарм) + статус «бомж».
3. Упрощённая заявка (`Application`) на покупку первой локации → привязка первой
   `Location` к пользователю.
4. `Gang`, `GangMember`, `GangHierarchyPost`, `GangLocation` — общая база для
   группировок.
5. Группировка «Воры»: `TheftAttempt`, механика «пойти на дело».
6. Группировка «Проститутки»: `EscortSession`, механика платной встречи.
7. `civic_role` = полицейский участок: штраф/протокол/проверка на группировку,
   `PoliceRecord`.
8. `chatUser.civic_role= DIRECTOR` = банк: `Deposit`, начисление процентов шедулером.
9. `chatUser.civic_role = BUSINESSMAN` = рынок: `MarketStall`, `StallInventory`, `StallCashbox`.
10. Заглушка `RealEstateListing` — только сущность, без бизнес-логики.

После шага 9 цикл уже полностью замкнут и проходим: житель может зайти в игру,
заработать первую локацию, выбрать одну из двух группировок или пойти в структуру,
зарабатывать через неё, тратить в банке/на рынке. Всё, что описано в базовой
концепции сверх этого (полноценная мэрия с голосованиями, остальные виды бизнеса,
кастомизация, мини-игры, рынок недвижимости) — следующие независимые итерации
поверх той же ролевой модели и того же `RewardService`, без переделки уже
сделанного.

## 7. Четырёхслойная архитектура (общая модель данных)

Система строится из четырёх логических слоёв, каждый из которых отвечает за свою
часть данных и правил. Слои́ не являются строгими уровнями абстракции в коде
(отдельные модули/пакеты), а описывают **категорию ответственности** сущности.

Правило: если новая механика не ложится честно ни в один из четырёх слоёв —
создаётся новый примитив внутри Слоя 3, а не расширяется существующий не
подходящим по смыслу полем.

```

┌──────────────────────────────────────────────────┐
│  Слой 4: Доставка и автоматизация               │
│  Notification, Scheduler, PollResultHandler      │
├──────────────────────────────────────────────────┤
│  Слой 3: Процессы                                │
│  Application, Poll        │
├──────────────────────────────────────────────────┤
│  Слой 2: Правила и ресурсы                       │
│  Charter, Ledger, Quota, Inventory               │
├──────────────────────────────────────────────────┤
│  Слой 1: Идентичность и роли                     │
│  ChatUser, LocationPost, RoleGrant,              │
│  PersonLevel, PostRank                           │
└──────────────────────────────────────────────────┘
```

### 7.1 Слой 1 — Идентичность и роли

Базовые сущности, определяющие «кто есть кто» в системе:

- **ChatUser** — персонаж (житель района). Уже реализован.
- **LocationPost** — должность персонажа в системной локации. Уже реализован
  (`location_posts` с enum `LocationPostType`).
- **PersonLevel** — уровень персонажа (производное от XpUser). Вычисляется по
  таблице порогов, не хранится как отдельная сущность. Используется как гейт
  (порог входа) для профессий, голосования, инвентаря. См. раздел 10.
- **PostRank** — ранг внутри должности LocationPost. В отличие от PersonLevel,
  может уменьшаться (наказание). Привязан к конкретному LocationPost, а не к
  персонажу в целом. См. раздел 10.
- **RoleGrant** — обобщённая запись «персонаж X имеет роль Y на скоупе Z». Не
  единая таблица, а **индекс-описание** (см. примечание ниже). Реальный носитель
  роли — одна из пяти специализированных таблиц (Profession, chatUser.civic_role = BUSINESSMAN,
  chatUser.civic_role= DIRECTOR, civic_role, chatUser.gang_role), а RoleGrant — это view/агрегат для
  проверки прав «есть ли у персонажа роль типа POLICE_OFFICER в районе N».

**Примечание про RoleGrant:** В концепции (раздел 2) описаны пять независимых
слоёв ролей, и это принципиальное решение: `profession`, `chatUser.civic_role = BUSINESSMAN`,
`chatUser.civic_role= DIRECTOR`, `civic_role`, `chatUser.gang_role` — отдельные таблицы/сервисы, а не одна
таблица `roles` с полем type. RoleGrant как единая таблица не создаётся; вместо
него используется `LocationPost` (уже реализован) для должностей в системных
локациях и, в будущем, отдельные записи в `GangMember`/`chatUser.civic_role = BUSINESSMAN` для
остальных типов ролей. Термин «RoleGrant» в схеме — это **логическая концепция**
(«персонаж имеет роль»), а не физическая таблица.

### 7.2 Слой 2 — Правила и ресурсы

Сущности, определяющие, **в каких рамках** можно действовать и **чем** можно
распоряжаться:

- **Charter (Устав)** — свод правил района или группировки. Состоит из двух
  частей: «Генеральная линия» (неизменяемая база, задаётся администратором) и
  «Поправки» (формируются одобренными заявками/голосованиями). В MVP —
  заглушка/конфиг, без полноценной сущности.
- **Ledger (Леджер)** — учётная книга: балансы, счета, кассы. Реализован частично
  через `CoinBalance`, `TransactionLog` (RewardService), `Deposit`,
  `StallCashbox`, `Gang.treasuryBalance`.
- **Quota (Квота)** — лимиты и выделения: сколько энергии/монет выделено
  структуре или сотруднику. В MVP — фиксированные числа в коде; в будущем —
  таблица квот с каскадным распределением (губернатор → структура → сотрудник).
- **Inventory (Инвентарь)** — предметы, товары на складе, прилавки, личные вещи.
  В MVP — `StallInventory`, `StallCashbox`, `GangLocation`; в будущем —
  личный инвентарь персонажа.

### 7.3 Слой 3 — Процессы

Примитивы, через которые **совершаются значимые действия** в системе. Каждый
примитив — отдельная сущность со своим жизненным циклом, не объединяемая в одну
таблицу «процессов».

#### 7.3.1 Application (Заявка)

Уже реализована (`applications` с enum `ApplicationType`). Обрабатывается через
стратегию (`ApplicationHandler` по `ApplicationType`). В MVP — автоодобрение,
в будущем — модерация и голосования.

**Планируемые типы Application (расширяемый список):**
- `BUY_FIRST_LOCATION` — ✅ реализовано
- `JOIN_GANG` — входит в MVP (шаг 4–6)
- `NOMINATE_CANDIDATE` — для выборов (сценарий №2)
- `EXPAND_STAFF` — расширение штата мэрии (раздел 0.4 концепции)
- `APPEAL` — апелляция на отказ мэрии (раздел 0.4 п.3, раздел 8)
- `RECALL_ELECTION` — инициирование переизбрания (сценарий №2, «обжаловать мэра»)
- `RECALL_GOVERNOR` — отзыв губернатора (импичмент)

#### 7.3.2 Poll (Голосование)

Коллективный процесс выбора одного из вариантов голосами участников. Результат —
победивший вариант (кандидат или «да»/«нет»). **Не реализован**, заказы в
сценарий №2.

```java
// Проект сущности
class Poll {
  Long id;
  ScopeType scopeType;       // DISTRICT, PARLIAMENT, GANG
  Long scopeId;              // districtId / gangId
  Long locationId;           // системная локация, на которой проходит голосование
  PollType pollType;         // ELECTION, AMENDMENT_VOTE, RECALL, COMMUNITY_CHOICE
  boolean hasCandidates;     // true — голосование за кандидатов, false — да/нет
  WeightStrategy weightStrategy;  // XP_USER_LEVEL, BY_POST_RANK, ONE_VOTE
  Instant startsAt;
  Instant endsAt;
  int quorumThreshold;       // порог явки в процентах
  PollStatus status;         // PENDING, ACTIVE, CLOSED, AUTO_ENACTED
  Long parentPollId;         // nullable: каскадное голосование (Парламент → Площадь)
  Long sourceApplicationId;  // nullable: заявка, породившая это голосование
}

class PollCandidate {
  Long id;
  Long pollId;
  Long characterId;         // кто выдвинулся
  String manifesto;         // предвыборная программа (текст)
  Instant nominatedAt;
}

class PollVote {
  Long id;
  Long pollId;
  Long candidateId;          // nullable: если hasCandidates=false, то null
  Long voterId;              // кто голосует
  double weight;             // вес голоса из WeightStrategy
  Instant votedAt;
}
```

**WeightStrategy** — pluggable-стратегия, определяющая вес голоса каждого
участника:
- `ONE_VOTE` — один человек = один голос (для Парламента)
- `XP_USER_LEVEL` — вес зависит от уровня XP-USER жителя (для «Площади Ленина»,
  раздел 3.1 концепции)
- `BY_POST_RANK` — вес зависит от должности в LocationPost (для Парламента,
  раздел 1 концепции)

**PollResultHandler** — интерфейс/стратегия, вызываемая шедулером (Слой 4) при
закрытии Poll. Регистрируется по `pollType`:
- `ELECTION` → создаёт/обновляет `LocationPost` для победителя
- `AMENDMENT_VOTE` → вносит поправку в Charter
- `RECALL` → отзывает LocationPost текущего губернатора, открывает новый ELECTION
- `COMMUNITY_CHOICE` → применяет косметический эффект к локации (без RoleGrant)

**Каскадные голосования** (раздел 0.4 концепции: Парламент → Площадь Ленина):
1. Application → Poll(scopeType=PARLIAMENT, weightStrategy=BY_POST_RANK)
2. Poll при закрытии (если >50% «за») → `PollResultHandler` создаёт
   `Poll(scopeType=DISTRICT, weightStrategy=XP_USER_LEVEL, parentPollId=...)`
3. Второй Poll при закрытии → handler вносит поправку в Charter

```


### 7.4 Слой 4 — Доставка и автоматизация

Инфраструктурные сервисы, не являющиеся игровыми сущностями, но обеспечивающие
работу процессов:

- **Notification** — уведомления (колокольчик в nav-rail). Таблица notifications:
  recipientCharacterId, title, body, notificationType, relatedEntityId, read,
  requiresAction/actionStatus и контекстные данные `data` (строка формата
  `key=value;key2=value2`, утилита `NotificationContextData` с экранированием).
  Для APPLICATION_RESULT в `data` кладутся `applicationType` и
  `applicationStatus` — фронтенд по ним решает, какие экраны/данные обновлять.
  Доставка: REST-история (NotificationController) + live WS-пуш в
  `/user/{username}/queue/notifications` (DTO `NotificationResponse`, в нём
  `data` распарсено обратно в Map). Модули events:
  ELECTION_STARTED, ELECTION_RESULT, APPLICATION_RESULT.
- **Scheduler** — фоновые задачи. Единая точка входа — `SchedulerGateway`
  (единственный `@Scheduled` в приложении, `fixedDelay = 15_000`), который
  диспетчеризует:
  - периодическую работу через интерфейс `TickHandler` (Spring собирает
    `List<TickHandler>`, каждый задаёт свой `intervalMillis()`; исключения
    ловятся и логируются, не роняя остальных);
  - отложенные проверки через реестр `ScheduledCheck` (таблица
    `scheduled_checks`: checkType, entityType, entityId, dueAt, timeoutAt,
    status PENDING/COMPLETED) → `ScheduledCheckHandler` по `checkType` —
    один индексный запрос просроченных вместо N полных сканов таблиц.
  Триггеры:
  - Закрытие Poll по истечении `endsAt` → `PollCloseCheckHandler` →
    `ElectionFacade.closeElection` (реестровая запись регистрируется при
    создании выборов; ручное закрытие гасит её через `cancelPending`)
  - Очистка протухших presence-сессий → `PresenceService.onTick()`
    (`TickHandler`, intervalMillis=15_000)
  - Начисление процентов по вкладам (банк, существующий `Deposit`)
  - Проверка истёкшей аренды прилавков (рынок)
  - «Живой участник» — обновление статуса активности (для сценария №2, порог 70%
    живых участников для переизбрания)
- **PollResultHandler** — интерфейс стратегии, регистрируемый по `PollType`.
  Вызывается шедулером при закрытии Poll. Может породить новый Poll, создать
  LocationPost, изменить Charter, начислить награды.
- **Событийная шина (DomainEventPublisher)** — инфраструктурный механизм
  коммуникации между сервисами разных слоёв на основе Spring `ApplicationEventPublisher`
  с персистентным event registry Modulith (`event_publication`). Сервисы Слоя 3
  публикуют события, не зная их подписчиков, а сервисы Слоя 4 подписываются через
  `@ApplicationModuleListener` (обёртка Modulith над `AFTER_COMMIT` с outbox-гарантиями:
  событие пишется в `event_publication` в транзакции публикатора и replay недоставленных
  после рестарта). Состав:
  - `DomainEvent` — абстрактный базовый класс события (eventId, occurredAt, type,
    actorId, targetId, scopeType, scopeId, payload); Jackson-совместимый
    (serializable, @JsonTypeInfo + @JsonSubTypes — конкретные события
    регистрируются здесь, без этого десериализация из outbox падает)
  - `EventType` — enum типов событий (APPLICATION_RESOLVED, ELECTION_CLOSED,
    COINS_CHANGED, NOTIFICATION_SENT и т.д.)
  - `ScopeType` — enum области действия (CHARACTER, DISTRICT, GLOBAL)
  - `DomainEventPublisher` — `@Service`, обёртка над `ApplicationEventPublisher`,
    через которую сервисы публикуют события
  - Конкретные события: `ElectionClosedEvent` (Этап 2), `CoinsChangedEvent`/
    `XpChangedEvent` (Этап 3), `ApplicationResolvedEvent` (Этап 4),
    `CharacterUpdatedEvent` (см. ниже)
  - Подписчики регистрируются по `EventType` в отдельных `@Service` +
    `@ApplicationModuleListener` (событие доставляется асинхронно на
    TaskExecutor после коммита транзакции публикатора);
    `@TransactionalEventListener` на подписчиках НЕ используется
  - `ApplicationResolvedEvent` — публикуется `ApplicationService` после
    разрешения заявки (handler.handle() + save); несёт applicationId,
    userId (ВНЕШНИЙ User.id — поле `Application.userId`, а не внутренний
    ChatUser.id), characterId (ВНУТРЕННИЙ ChatUser.id, за которого подана
    заявка — поле `Application.characterId`; добавлено для адресности:
    уведомление уходит конкретному персонажу, а не всем персонажам
    пользователя), applicationType и status — **строки** (имена enum
    ApplicationType/ApplicationStatus: APPROVED/REJECTED), а не сами enum:
    событие живёт в `core.event` и не должно зависеть от модуля civic
    (границы модулей). resultMessage в событие НЕ входит — подписчик
    формирует текст уведомления сам по статусу (это также держит
    сериализованный JSON короче лимита `event_publication.serialized_event`
    varchar(255)); подписчик `NotificationEventListener.onApplicationResolved`
    находит персонажа по `characterId`, сохраняет уведомление
    (тип APPLICATION_RESULT, relatedEntityId = applicationId) с контекстом
    `data={applicationType, applicationStatus}` (сериализация
    NotificationContextData) и шлёт WS-пуш этому персонажу. Фронтенд по
    `data.applicationType`/`data.applicationStatus` решает, нужно ли
    перезагружать профиль (паспорт/лицензия обновляют ChatUser, остальные
    заявки — нет; основной канал обновления профиля — отдельное событие
    `CharacterUpdatedEvent` → `/user/queue/character-updated`, см.
    architecture/reactive-character-updates.md).
    
  **Правила использования:**
  - Сервисы Слоя 3 не вызывают сервисы Слоя 4 напрямую — вместо этого публикуют
    событие через `DomainEventPublisher`
  - Сервисы Слоя 4 (Notification, PollResultHandler, RewardService) подписываются
    на события через `@ApplicationModuleListener`
  - `DomainEvent` не хранится в БД — это транспортный объект. Постоянное хранение
    — ответственность подписчика (например, Notification сохраняется в БД)
  - В multi-instance режиме (Kubernetes) `ApplicationEventPublisher` заменяется
    на внешнюю шину (Kafka/RabbitMQ) без изменения логики подписчиков

### 7.5 Связи между слоями (направление)

Слой 1 → Слой 2 → Слой 3 → Слой 4 — это **зависимость по данным**: Слой 1
определяет, кто может инициировать процесс; Слой 2 — с какими ресурсами и в
каких рамках; Слой 3 — сам процесс; Слой 4 — уведомление и автоматическое
завершение.

Обратное направление (Слой 4 → Слой 1/2) — через handler'ы: PollResultHandler
может создать/отозвать LocationPost (Слой 1) или поправить Charter (Слой 2).

## 9. Связь с концепцией (concept.md)

Четырёхслойная модель не заменяет, а **упорядочивает** существующую концепцию:

- Разделы 0, 1, 2 концепции (иерархия мэрии, роли) → Слой 1
- Раздел 3 (экономический цикл: XP, энергия, монеты), раздел 5 (бизнес-локации),
  раздел 8 (системные локации) → Слой 2
- Раздел 0.4, 0.6 (заявки, расширение штата), раздел 6 (группировки — часть
  процессов), сценарий №2 (выборы) → Слой 3
- Раздел 0.7 (нотификации о старте/завершении), раздел 4.5 (ежедневные квесты —
  триггер через шедулер) → Слой 4

При расхождении между архитектурной моделью (этот документ) и концепцией
(concept.md) приоритет имеет код, затем — концепция (как намерение), затем —
архитектурная модель (как вспомогательное описание для AI).

## 10. Уровни: PersonLevel и PostRank

Два отдельных механизма управления прогрессией персонажа: **общий уровень**
(порог входа) и **ранг внутри должности** (прогрессия/наказание).

### 10.1 PersonLevel — общий уровень персонажа

**Что это:** Производное значение от `XpUser`, вычисляемое по таблице порогов.
Не хранится как отдельная сущность, а вычисляется на лету или кэшируется.

**Принципы:**
- Только растёт — никогда не понижается, так как сам `XpUser` не убывает
  (раздел 3.1 концепции: «XP-USER — только начисляется»).
- Является **гейтом** (порогом входа) для механик, а не игровой валютой.

**Где используется (гейты):**
- Доступ к профессиям (`Profession`) — минимальный уровень для открытия
  каждой профессии задаётся в её конфиге.
- Бронирование/покупка локаций — концепция раздел 2.1.
- Доступ к инвентарю и кастомизации — более крутой инвентарь требует
  более высокого уровня.
- Вес голоса в `Poll` — `WeightStrategy.XP_USER_LEVEL` использует уровень
  (а не сырой XP) для расчёта веса голоса (раздел 3.1 концепции).
- Минимальный уровень для получения `LocationPost`, `chatUser.civic_role= DIRECTOR`,
  `civic_role` — задаётся Уставом района (Charter) или конфигом должности.

**Таблица порогов (LevelThreshold):**

```java
class LevelThreshold {
  int level;              // номер уровня, начиная с 1
  long xpRequired;        // сколько XP-USER нужно для достижения этого уровня
  String title;           // необязательное название ранга (например, «Новичок»)
}
```

Пример: уровень 1 = 0 XP, уровень 2 = 100 XP, уровень 3 = 300 XP и т.д.
Конкретные значения задаются в конфиге/БД и могут меняться балансировкой.

### 10.2 PostRank — ранг внутри должности (общий переиспользуемый примитив)

**Что это:** Универсальная сущность, привязанная к конкретному `LocationPost`
(должности персонажа в системной локации). Позволяет реализовать прогрессию
и **наказание** внутри должности — то, что невозможно через `XpUser`/`PersonLevel`,
так как они только растут.

**Ключевое отличие от PersonLevel:** `rank` и `rankXp` могут **уменьшаться**
(наказание за ошибку). Это отдельный счётчик, привязанный к `LocationPost`,
а не к персонажу в целом — если персонаж теряет должность, `PostRank` этой
должности обнуляется/архивируется вместе с ней.

```java
class PostRank {
  Long id;
  Long locationPostId;     // FK на LocationPost (должность персонажа)
  int rank;                // текущий ранг/звание, может расти И понижаться
  long rankXp;             // опыт ранга, отдельный от XP-USER
  Instant lastChangedAt;
}
```

**Где применяется в MVP:**
- `POLICE_OFFICER` — согласно концепции (раздел 4.6), полицейский теряет
  звание/lvl в участке за ошибку при проверке. Это прямое использование
  `PostRank`: `rank` растёт за успешные проверки, падает за ошибки.

**Где НЕ применяется (пока):**
- Выборные должности (`GOVERNOR`, `MAYOR`, `DEPUTY`) — они либо есть у
  персонажа, либо нет; внутренней прогрессии в концепции не описано.
- Назначаемые должности (`BANK_DIRECTOR`, `REAL_ESTATE_DIRECTOR`) —
  аналогично, без прогрессии в концепции.
- Роли группировок (`chatUser.gang_role`) — для них уже есть отдельный аналог
  (`XP-GANG`, раздел 3.1 концепции), который играет роль «ранга в
  группировке».

**Как расширять:**
Если в будущем у какой-то другой должности появляется описанная в концепции
прогрессия/наказание — достаточно создать `PostRank` для соответствующего
`LocationPost`, без правки схемы или добавления новых полей в `civic_role`.
Механизм уже общий и переиспользуемый.
