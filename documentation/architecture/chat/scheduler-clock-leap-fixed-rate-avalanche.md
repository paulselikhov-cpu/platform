# Лавина планировщиков при скачке системных часов (clock leap)

## Проблема

При скачке системных часов (NTP-синхронизация, перевод времени) планировщики на
`@Scheduled(fixedRate)` начинали выполнять метод **каждую миллисекунду** — лавина
вызовов, упирающаяся в БД и WS-рассылку. Процесс залипал, порт 8080 не
освобождался, Spring Boot не стартовал.

## Причина

`ScheduledThreadPoolExecutor` при `fixedRate` планирует следующий запуск **от
начала предыдущего**: `next = startTime + period`. Если системные часы ушли вперёд
и «пропущенная» работа накопилась, исполнитель компенсирует её лавиной
последовательных запусков с нулевой задержкой — пока не «догонит» расписание.

Это особенность `DelayQueue`/`ScheduledThreadPoolExecutor`: задержка считается как
`time - now`, и при `time << now` она становится отрицательной, а отрицательная
задержка = немедленный запуск.

## Затронутые классы

| Класс | Метод | Было | Стало |
|-------|-------|------|-------|
| `poll/scheduler/ElectionScheduler` | `closeExpiredElections` | `@Scheduled(fixedRate = 60_000)` | `@Scheduled(fixedDelay = 60_000)` |
| `chat/service/onlineSessions/PresenceService` | `cleanupStalePresences` | `@Scheduled(fixedRate = 15_000)` | `@Scheduled(fixedDelay = 15_000)` |

> **Обновление (Этап 5 событийной архитектуры, 2026-08-06):** все фоновые
> задачи переведены на единый `core.scheduler.SchedulerGateway` — единственный
> `@Scheduled(fixedDelay = 15_000)` в приложении. Периодические задачи
> реализуют `TickHandler` (`onTick()` + `intervalMillis()`), отложенные
> проверки идут через реестр `ScheduledCheck` → `ScheduledCheckHandler`.
> Отдельные `@Scheduled` на классах (`ElectionScheduler`,
> `PresenceService.cleanupStalePresences`) удалены, поэтому правило
> «fixedDelay вместо fixedRate» теперь соблюдается централизованно.

## Фикс

Заменить `fixedRate` на `fixedDelay`:

- `fixedDelay` планирует следующий запуск **от завершения предыдущего** —
  задержка всегда положительная, не зависит от системных часов и не
  «компенсирует» пропущенные интервалы лавиной.
- Для периодических фоновых задач (очистка протухших presence, закрытие
  просроченных выборов) точность интервала не критична — важна регулярность,
  поэтому `fixedDelay` — правильный выбор.

## Правило на будущее

- `@Scheduled(fixedRate)` — только если задача **обязана** срабатывать строго
  каждые N мс независимо от длительности выполнения (например, отдача кадров).
- Для всех остальных фоновых периодических задач использовать `fixedDelay`.
- `@EnableScheduling` находится в `com.platform.PlatformApplication`.
