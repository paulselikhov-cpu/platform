# BabichChat — бриф для AI-разработчика: MVP экономического и ролевого слоя

> **Кратко:** Техническое задание на MVP — минимальный связный цикл экономики и ролей.
> Что уже реализовано: экономический слой (монеты, XP, энергия, RewardService),
> профессия «дворник», покупка первой локации через заявку, система районов.
> Что предстоит: группировки (Воры, Проститутки), полицейский участок, банк, рынок.
> Порядок реализации — раздел 6.
>
> **Оглавление:**
> - Раздел 0 — Что уже есть (отправная точка)
> - Раздел 1 — Скоуп MVP (что делаем, что откладываем)
> - Раздел 2 — Базовый экономический цикл
> - Раздел 3 — Группировки: Воры и Проститутки
> - Раздел 4 — Структуры: полиция, банк, рынок
> - Раздел 5 — Роли (список сущностей)
> - Раздел 6 — Итоговый порядок реализации (главное!)

Этот документ адресован AI-агенту, который будет дорабатывать существующий backend
(Java/Spring) и frontend (Angular) чата. Он написан как техническое задание поверх
общей концепции (`babichchat_concept.md, districts-and-public-locations.md`), но сужен до **первого работающего MVP**:
минимального, но полностью связного цикла, который потом расширяется модульно.
Приоритет — реализовать функционал из концепции; существующий код при этом можно и
нужно менять, если это требуется для результата, а не сохранять в неизменном виде
любой ценой.

## 0. Что уже есть (отправная точка, а не жёсткое ограничение)

Текущий код — уже рабочий каркас онлайн-чата (backend на Java/Spring, frontend на
Angular). Базовые сущности вроде пользователя, локаций (публичных/приватных),
каналов внутри локации и сообщений уже реализованы и работают — изучи фактический
код, а не описания, чтобы понять точную текущую структуру данных и API.

Твоя задача — нарастить поверх этого экономический слой (монеты, XP, энергия),
ролевую систему и первые игровые структуры, ориентируясь в первую очередь на
**достижение функционала из концепции**, а не на сохранение существующих сущностей
любой ценой. Если для реализации задуманного функционала существующую сущность
нужно расширить полями, изменить связи или переписать — делай это; переиспользование
кода приветствуется, но не в ущерб результату. Ориентиры:
1. В итоге должен получиться один **связный цикл**, который реально проходится от
   начала до конца: житель без денег и локации → зарабатывает → покупает первую
   локацию → может пойти в группировку или структуру → зарабатывает там → тратит.
2. Новые игровые сущности (экономика, роли, группировки, структуры) стоит по
   возможности отделять собственными таблицами/сервисами (см. раздел 8), чтобы дальше
   их можно было независимо расширять — но это ориентир, а не догма важнее
   работающего функционала.

## 1. Скоуп MVP (что делаем сейчас, что откладываем)

### Делаем сейчас
1. Экономический слой: монеты, XP-USER, энергия, единый сервис начислений
   (`RewardService`) с логом транзакций.
2. Статус «бомж» → профессия «дворник» (тап-фарм) → покупка первой локации.
3. **Упрощённая мэрия** — не полноценная система голосований, а минимальный сервис
   одобрения заявок (для MVP можно автоматически одобрять заявки на покупку первой
   локации/вступление в группировку — но через ту же структуру данных `Application`
   (заявка), чтобы в будущем заменить автоодобрение на реальное голосование без
   переделки модели).
4. Две группировки: **Воры** и **Проститутки** (см. раздел 3).
5. Одна гражданская структура: **Полицейский участок** (`civicRole`, упрощённая
   версия — см. раздел 4.1).
6. Один appointedRole-сервис: **Банк** (упрощённая версия — см. раздел 4.2).
7. **Рынок (общий)** — аренда прилавков без мэрии (см. раздел 4.3).

### Закладываем архитектурно, но НЕ реализуем логику сейчас
- **Рынок недвижимости** — завести сущность-заглушку (например, таблицу `Listing`
  с полями locationId, sellerId, price, status), но бизнес-логику купли-продажи,
  комиссию appointedRole-владельца рынка и т.д. не писать. Это отдельный будущий
  модуль.
- Полноценная мэрия с Парламентом, «Площадью Ленина», голосованиями, каскадным
  распределением энергии между структурами — архитектурно предусмотрена (см. раздел
  8), но в MVP работает в упрощённом/заглушечном виде.
- Мини-игры, кастомизация, дневные квесты, остальные виды бизнеса (клуб, кафе,
  мебельный и т.д.) — не в этой итерации.

## 2. Базовый экономический цикл MVP

```
Регистрация → житель без локации ("бомж")
      → работает дворником (тап-фарм, тратит энергию, получает монеты + чуть XP)
      → копит монеты → покупает первую локацию (студия-хрущёвка) через упрощённую
        заявку в мэрию (в MVP — автоодобрение)
      → теперь у жителя есть локация → появляется личная спальня для восстановления
        энергии (см. 2.3)
      → житель может: (а) продолжать качать профессию, (б) вступить в группировку
        (Воры или Проститутки) по приглашению, (в) устроиться в структуру
        (полицейский участок), (г) арендовать прилавок на рынке
      → заработанные монеты тратятся: аренда/содержание локации, покупка вклада в
        банке, покупка товара для прилавка и т.д.
```

### 2.1 Сущности экономики
- `CoinBalance` (у User) — просто числовое поле или отдельная таблица с историей.
- `XpUser`, `XpGang` — накопительные счётчики, никогда не уменьшаются.
- `Energy` — текущее значение + таймстамп последнего пересчёта (чтобы не хранить
  тикающий таймер, а вычислять «сколько накопилось» на лету при каждом запросе).
- `RewardService` — единая точка входа для любого начисления/списания монет и XP,
  принимает `reason` (enum: `WORK_SHIFT`, `GANG_TRIBUTE`, `POLICE_FINE`,
  `BANK_INTEREST`, `MARKET_SALE` и т.д.) и пишет запись в `TransactionLog`.

### 2.2 Профессия «дворник» (единственная профессия MVP)
- Тап-действие: житель нажимает кнопку «работать», сервис проверяет остаток
  энергии, списывает фиксированную порцию энергии, начисляет фиксированную монету
  (+ немного XP-USER) через `RewardService`.
- Rate-limit на уровне API обязателен даже для MVP (защита от скриптового спама
  кнопки).

### 2.3 Энергия в MVP
- Восстановление: упрощённо — пассивный таймер (+1 каждые N минут), без полноценной
  механики сна на старте. Разделение по локации/уровню (потолок 30–50% от сна) можно
  добавить отдельной итерацией — заложи в модели поле `energyRegenSource`
  (`PASSIVE`/`SLEEP`/`FOOD`), чтобы потом не переделывать таблицу.
- Кулдауны и текущая энергия — в Redis (TTL), не в клиентском времени.

### 2.4 Заявки (`Application`)
Даже для MVP заведи заявки как отдельную сущность с полем `type` (enum,
расширяемый): `BUY_FIRST_LOCATION`, `JOIN_GANG` и т.д. Обработчик для каждого типа —
отдельный класс/сервис (стратегия). В MVP большинство типов просто автоодобряются
сразу после создания — но структура данных (кто подал, когда, какой статус, кто
рассматривал) должна уже поддерживать будущую замену на реальное голосование.

## 3. Группировки: Воры и Проститутки (первые две в MVP)

### 3.1 Общая для обеих группировок модель данных
- `Gang` (id, type: `THIEVES`/`PROSTITUTES`, name, level, treasuryBalance, energyPool).
- `GangMember` (userId, gangId, nicknameGang — скрытый ник, hierarchyPostId).
- `GangHierarchyPost` (gangId, title, slotsCount, minXpGang, canParticipateInExile —
  флаг для механики свержения лидера, вне скоупа MVP, но поле можно завести сразу).
- `GangLocation` — отдельная приватная `Location`, видимая только участникам банды
  (используй существующий тип Location с флагом `visibility = GANG_ONLY` и привязкой
  к `gangId`).
- Вступление — только по приглашению лидера/по заявке через `Application` типа
  `JOIN_GANG`.
- У обеих группировок в статусе жителя (публичном профиле) отображается **фейковая
  профессия** — например «дворник» или «швея» — вместо реальной механики; реальный
  заработок идёт через `gangRole`, не через `profession`.

### 3.2 Группировка «Воры» (эталонный пример для симметрии)

**Идея:** участник не работает по обычной профессии — вместо этого совершает
«кражи», результат которых уходит в общак банды, а сам участник получает
«зарплату» из общака.

**Механика по шагам:**
1. Участник инициирует действие «пойти на дело» (аналог тап-фарма/смены, тратит
   энергию, есть кулдаун).
2. Сервис бросает бросок (шанс успеха зависит от `XpGang` участника и, опционально,
   от «защищённости» цели/локации — в MVP можно упростить до фиксированного
   процента успеха).
3. При успехе: в общак банды (`treasuryBalance`) зачисляется случайная сумма монет
   (диапазон растёт с уровнем `XpGang` участника), сам участник получает XP-GANG,
   плюс фиксированную «зарплату» из общака (через `RewardService`, `reason:
   GANG_TRIBUTE`).
4. При провале: риск — сообщение в лог полиции (см. 4.1) с шансом, что полицейский
   позже «спалит» участника, вбив его никнейм в базу.
5. Украденные предметы (если есть инвентарная механика — вне MVP) в будущем можно
   перепродавать на рынке под другим названием — не реализуем в MVP, но сущность
   `MarketListing` стоит сразу иметь поле `originalItemId` (nullable) под эту
   будущую логику подмены.

**Анти-фрод:** лимит успешных «дел» в сутки на одного участника (через Redis TTL,
как у энергии).

### 3.3 Группировка «Проститутки» (детализируем по аналогии с «Ворами»)

**Идея:** та же схема «фейковая публичная профессия → скрытая монетизация через
приватные платные встречи с другими жителями → общак → зарплата», но вместо
случайного «броска на успех кражи» — это **сделка с согласия двух сторон**
(житель-клиент сам инициирует и платит).

**Механика по шагам:**
1. Участница/участник группировки открывает у себя в профиле (видно только тем, кто
   знает — например, через отдельный публичный тег `escortAvailable`, не выдающий
   принадлежность к банде) предложение платной «встречи» с указанием цены в
   монетах. Цена может расти вместе с `XpGang` — чем выше уровень, тем выше
   допустимый ценовой диапазон (упрощённо: `minPrice`/`maxPrice`, вычисляемые от
   `XpGang`).
2. Другой житель (клиент) инициирует заявку на «встречу» в приватной локации
   (например, в своей или её квартире).
   Клиент подтверждает оплату согласованной суммы монет.
3. Сервис списывает монеты у клиента и делит сумму:
   - Основная часть уходит в общак банды (`treasuryBalance`), как «дань» —
     аналогично тому, как у воров украденное уходит в общак.
   - Небольшой фиксированный процент участница получает на руки сразу (личные
     монеты, чтобы бы была ощутимая моментальная награда, а не только зарплата
     из общака).
   - Участница получает **XP-USER** напрямую за «встречу» (в отличие от воров, где
     основной выход — монеты в общак, здесь по замыслу концепции акцент на
     получении опыта, а не денег напрямую).
4. Периодически (как и у воров) участница получает «зарплату» из общака —
   `RewardService`, `reason: GANG_TRIBUTE`.
5. Риск разоблачения — тот же полицейский механизм (4.1): полицейский, заметив
   подозрительную частоту приватных «встреч» жителя, может попытаться вбить в базу
   её `nicknameGang`; при правильной догадке — полицейский получает награду и метку
   ставится в полицейскую базу, при ошибке — полицейский несёт наказание (см. 4.1).

**Анти-фрод:** лимит на количество оплаченных «встреч» с одним и тем же клиентом в
сутки (та же логика лимита пары пользователей, что у реакций/подарков/краж — не
даём двум сговорившимся аккаунтам бесконечно перекачивать монеты друг другу под
видом «встреч»).

**Данные:** заведи отдельную таблицу `EscortSession` (gangMemberId, clientId,
price, xpAwarded, gangCut, personalCut, timestamp, locationId) — по аналогии можно
завести `TheftAttempt` (gangMemberId, success, amount, timestamp) для воров, чтобы
обе группировки имели симметричную, но раздельную историю транзакций для
анти-фрода и будущей аналитики.

## 4. Структуры MVP: полицейский участок, банк, рынок

Формат ниже — как конкретный проходимый сценарий (по аналогии с примером
«pashaSelikhov» из базовой концепции), чтобы было видно, как это работает от
кнопки до записи в базе.

### 4.1 Полицейский участок (`civicRole`, упрощённая версия)

**Роль:** `POLICE_OFFICER` — назначается вручную (для MVP: администратором
платформы/через упрощённую заявку без полноценного голосования мэрии). Слотов на
район — фиксированное небольшое число (например, 3).

**Энергия в MVP:** пока нет полноценной каскадной системы мэрии (раздел 8 базовой
концепции), у каждого `POLICE_OFFICER` — **фиксированная дневная квота энергии**
(например, 20 очков в сутки, хранится в Redis с TTL до полуночи). Позже эта квота
заменяется на каскадное распределение от структуры/губернатора — без изменения
того, как сама роль тратит энергию.

**Действия и их стоимость (пример):**
| Действие | Энергия | Эффект |
|---|---|---|
| «Оштрафовать» | 2 | Списывает монеты у указанного жителя, часть уходит в бюджет мэрии (`reason: POLICE_FINE`) |
| «Составить протокол» | 1 | Косметическая запись в публичном логе локации, без экономического эффекта |
| «Проверить на связь с группировкой» | 5 | См. сценарий ниже |

**Сценарий (по образцу базового примера):**
1. Полицейский Иванов подозревает, что житель с ником `pashaSelikhov` состоит в
   группировке «Воры» (например, заметил частые заявки `TheftAttempt` с провалом
   рядом с этим жителем, или просто по RP-логике).
2. Иванов открывает форму «Проверить на связь с группировкой» в интерфейсе
   участка, вводит целевого жителя и предполагаемый тип группировки.
3. Сервис сверяет реальную запись `GangMember.nicknameGang` (скрыто от всех, кроме
   этой проверки) с введённым предположением.
4. Если совпадение — начисление монет Иванову (`RewardService`, `reason:
   POLICE_GANG_CATCH`) + запись в публичную полицейскую базу
   (`PoliceRecord: userId, gangType, catchDate, officerId`).
5. Если совпадения нет — штраф самому Иванову: понижение его `XpGang`-аналога для
   civicRole (условно «звание» полицейского) или временная блокировка действия
   «Проверить на связь» на сутки (реализуй как самое простое наказание для MVP —
   например, откат потраченной энергии не даём, плюс кулдаун-штраф).

### 4.2 Банк (`appointedRole`, упрощённая версия)

**Роль:** `BANK_DIRECTOR` — один слот на район, назначается (для MVP — вручную
администратором/автозаявкой). Без директора банк не принимает новые вклады
(read-only витрина).

**Действия жителя:**
- «Открыть вклад» — житель вносит сумму монет на фиксированный срок под
  фиксированный процент (в MVP — жёстко закодированная ставка, например 5% за 3
  дня, без реального рынка ставок).
- «Забрать вклад» — доступно только после истечения срока; при досрочном
  закрытии — без процентов (штраф за досрочность, простая логика для MVP).

**Сценарий:**
1. Житель Смирнова открывает вклад на 500 монет на 3 дня под 5%.
2. Сервис списывает 500 монет со счёта Смирнова, создаёт запись `Deposit`
   (userId, amount=500, rate=0.05, openedAt, maturesAt, status=ACTIVE).
3. Фоновая задача (шедулер) проверяет каждый день истёкшие вклады.
4. По истечении срока: Смирнову начисляется 500 + 5% = 525 монет
   (`RewardService`, `reason: BANK_INTEREST`); из процента часть (например, 1 из
   5 процентных пунктов) уходит в бюджет мэрии как комиссия банка
   (`reason: BANK_FEE_TO_TREASURY`) — это то, что «кормит» мэрию, по базовой
   концепции.

**Данные:** `Deposit` (id, userId, amount, rate, openedAt, maturesAt, status).

### 4.3 Рынок (общий, аренда прилавков — единственный бизнес без мэрии)

**Роль:** `businessRole` типа `MARKET_STALL_OWNER` — выдаётся сразу при аренде,
без заявки в мэрию (в отличие от «настоящего» бизнеса).

**Сценарий:**
1. Житель Кузнецова арендует прилавок за 50 монет на сутки (`MarketStall`:
   id, ownerId, rentedUntil).
2. Кузнецова становится `businessRole` (MARKET_STALL_OWNER) и получает доступ к
   личному мини-складу прилавка (`StallInventory`: stallId, itemId, quantity,
   pricePerUnit).
3. Кузнецова закупает товар на системном складе (или вручную заводит позиции для
   MVP, если склад ещё не реализован) — например, 10 единиц «самогона» по 2 монеты
   за штуку закупки, выставляет на прилавке по 5 монет за штуку.
4. Другой житель заходит на локацию «Рынок», видит прилавок, покупает 1 единицу —
   сервис списывает 5 монет у покупателя, зачисляет их в кассу прилавка
   (`StallCashbox`), уменьшает `quantity` на 1.
5. Кузнецова заходит и «снимает кассу» — деньги переводятся на личный баланс
   (`RewardService`, `reason: MARKET_SALE`).
6. По истечении срока аренды (`rentedUntil`), если не продлить — прилавок
   закрывается, `businessRole` снимается, остаток товара «сгорает» или
   возвращается в личный инвентарь (реши по вкусу, не критично для MVP).

**Анти-АФК:** фоновая задача проверяет истёкшую аренду и деактивирует прилавки.

### 4.4 Рынок недвижимости (только сущность-заглушка, без логики)

Заведи `RealEstateListing` (id, locationId, sellerId, price, status: `DRAFT` —
и больше ничего). Не подключай никакой бизнес-логики купли-продажи, комиссии
`appointedRole`-владельца рынка и т.п. — это осознанно отложено на следующую
итерацию после того, как MVP-цикл заработает.

---

## 5. Роли — итоговый список сущностей для MVP

Заведи с самого начала пять отдельных таблиц/сервисов (даже если некоторые в MVP
почти пустые) — это тот же принцип, что и в базовой концепции:

- `Profession` (пока только `DVORNIK`)
- `BusinessRole` (пока только `MARKET_STALL_OWNER`)
- `AppointedRole` (пока только `BANK_DIRECTOR`)
- `CivicRole` (пока только `POLICE_OFFICER`)
- `GangRole` (у каждого `GangMember` — привязка к `GangHierarchyPost`)
- `SystemRole` (admin/moderator — обычный RBAC, не связан с игровой логикой)

Не объединяй их в одну таблицу «roles» с полем type — это тот момент, который
позже больнее всего аукнется при расширении (полномочия/лимиты/энергия у каждого
типа принципиально разные).

---

## 6. Итоговый порядок реализации (рекомендуемый)

1. `RewardService` + `TransactionLog` + монеты/XP-USER/энергия поверх
   существующего `User`.
2. Профессия «дворник» (тап-фарм) + статус «бомж».
3. Упрощённая заявка (`Application`) на покупку первой локации → привязка первой
   `Location` к пользователю.
4. `Gang`, `GangMember`, `GangHierarchyPost`, `GangLocation` — общая база для
   группировок.
5. Группировка «Воры»: `TheftAttempt`, механика «пойти на дело».
6. Группировка «Проститутки»: `EscortSession`, механика платной встречи.
7. `CivicRole` = полицейский участок: штраф/протокол/проверка на группировку,
   `PoliceRecord`.
8. `AppointedRole` = банк: `Deposit`, начисление процентов шедулером.
9. `BusinessRole` = рынок: `MarketStall`, `StallInventory`, `StallCashbox`.
10. Заглушка `RealEstateListing` — только сущность, без бизнес-логики.

После шага 9 цикл уже полностью замкнут и проходим: житель может зайти в игру,
заработать первую локацию, выбрать одну из двух группировок или пойти в структуру,
зарабатывать через неё, тратить в банке/на рынке. Всё, что описано в базовой
концепции сверх этого (полноценная мэрия с голосованиями, остальные виды бизнеса,
кастомизация, мини-игры, рынок недвижимости) — следующие независимые итерации
поверх той же ролевой модели и того же `RewardService`, без переделки уже
сделанного.
